# 一、先理解脚本的基本组成

一套脚本主要涉及以下文件和逻辑：

```text
BP.ini / banpick.ini
    ↓
禁用、首发、出战
    ↓
切换.ini
    ↓
普通切换 / 特判切换 / 中切 / 死切 / 击杀切换
    ↓
精灵.ini
    ↓
登场 / 中切登场 / 死切登场
    ↓
循环 / 特判循环 / 击杀
    ↓
吃药 / 切走 / 其他动作
```

其中有三个文件尤其重要：

```text
BP.ini
切换.ini
某个精灵.ini
```

它们承担的职责不同：

**BP.ini**

负责：

- Ban 哪些精灵；
- 谁首发；
- 哪些精灵进入出战池；
- 某些特定 Ban 条件下改用哪套阵容。

**切换.ini**

负责：

- 根据敌我双方精灵判断换谁；
- 普通特判切换；
- 全局切换；
- 死亡切换；
- S 特判；
- T 特判；
- 击杀切换；
- 中切相关切换。

**精灵.ini**

负责该精灵本身：

- 循环；
- 登场；
- 击杀；
- 中切登场；
- 死切登场；
- 需要时的特判出招；
- `切走`；
- `hp` / `pp` 等动作。

---

# 二、脚本最重要的状态概念

开发时首先必须明确：

> “登场”不是一种状态。

至少存在：

1. 同起登场；
2. 中切登场；
3. 死切登场；
4. 中切特判登场。

此外，切换本身又分：

1. 普通切换；
2. 特判切换；
3. 全局切换；
4. S 死切特判；
5. T 独立特判；
6. 击杀切换；
7. 中切切换；
8. 针对死切的死亡切换。

所以不要把所有“换精灵”简单理解成：

```text
切走 → 登场
```

真正的运行关系是：

```text
为什么换？
↓
什么时候换？
↓
属于哪一种换？
↓
是否存在特判？
↓
是否存在对应状态下的登场技？
↓
没有时再进入默认逻辑。
```

---

# 三、精灵脚本的基础写法

一个精灵可以包含：

```text
[循环]
默认=……

[登场]
默认=……

[击杀]
默认=……

[中切登场]
默认=……

[死切登场]
默认=……
```

例如截图中的简单脚本：

```ini
[循环]
默认=pp hp hp

[登场]
默认=切走

[死切登场]
默认=1 hp
```

另一个例子：

```ini
[循环]
默认=切走 hp

[登场]
默认=特判切走

[击杀]
默认=1
```

需要特别注意：

> `[登场]`、`[中切登场]`、`[死切登场]` 是彼此独立的配置区域。

没有某个专用区域时，部分状态会按照兼容逻辑回退。

---

# 四、普通登场、中切登场、死切登场

## 4.1 普通登场

普通 `[登场]` 对应的是：

> 同起状态。

也就是双方同时换精灵、首发建立等同起情况。

原文特别强调：

> 双方同时切换精灵，下回合走登场，不是中切登场。

因此：

```text
双方同时换人
        ↓
同起
        ↓
[登场]
```

而不是：

```text
[中切登场]
```

---

# 五、实际的同起登场判定

截图中的流程可整理为：

```text
同起登场
   ↓
对面是否切精灵？
   ├─ 是 → 进入循环
   │
   └─ 否
       ↓
   是否存在登场技？
       ├─ 否 → 进入循环
       │
       └─ 是 → 使用登场技
                 ↓
        ┌──────────────┐
        │              │
     对方击杀       对方中切
        │              │
    中断击杀技       中断循环
        │              │
    继续下一状态    中断后续状态
```

因此：

> 登场技是一次性动作，不会自动作为循环继续执行。

截图明确注明：

> “登场技不会循环”。

---

# 六、中切

中切的核心特征：

> 我方主动中途切换时，回合进度与对方存在差异。

因此中切后的精灵必须区分：

```text
[登场]
```

和：

```text
[中切登场]
```

---

# 七、为什么必须区分中切登场

例如：

```text
我方精灵 A
    ↓
中途主动切出
    ↓
精灵 B 登场
```

此时 B 并不是“同起登场”。

因为 B 的实际回合状态与对面不一致。

所以使用：

```ini
[中切登场]
默认=……
```

---

# 八、被天尊驱逐也属于中切登场

截图中专门做了实例：

> 被天尊驱逐的中切登场。

也就是说：

```text
被天尊驱逐
     ↓
重新登场
     ↓
视为中切登场
```

所以相应脚本应考虑：

```ini
[中切登场]
默认=……
```

而不是只写普通 `[登场]`。

---

# 九、中切登场的实际流程

截图中的“非同起”流程可以概括为：

```text
非同起
 ↓
进入中切登场判断
 ↓
对面是否切精灵？
 ├─ 是 → 进入循环
 │
 └─ 否
      ↓
  我方是否切精灵 / 被驱逐？
      ├─ 否 → 进入循环
      │
      └─ 是
          ↓
      是否存在中切登场技？
          ├─ 否 → 进入循环
          │
          └─ 是 → 使用中切登场技
```

同时：

> 整套中切登场过程中的每一回合都会继续判断切换、死亡、击杀等状态。

如果中途再次发生中切、死亡、击杀，就会中断当前中切登场流程。

---

# 十、中切特判登场

2.4.2 增加：

> 中切特判登场。

它不是普通中切登场的简单升级，而是专门处理：

> 中切时使用“特判切走”的情况。

也就是：

```text
中切
 ↓
使用普通切走？
 └─ → 普通中切登场

中切
 ↓
使用特判切走？
 └─ → 中切特判登场
```

---

# 十一、中切特判登场的核心陷阱

这是非常容易写错的地方。

如果：

```text
某精灵存在中切特判登场方案
```

但：

```text
当前面对的精灵没有对应的中切特判登场方案
```

并不是简单地退回普通 `[中切登场]`。

规则是：

> 如果该精灵已经存在针对其他目标的中切特判登场方案，那么当前目标找不到方案时，打循环不会走中切登场。

只有：

> 这个精灵完全不存在任何中切特判登场方案，

才会正常走普通中切登场。

因此开发者要特别检查“部分覆盖”的问题。

---

# 十二、特判切与全局切换

截图中的 2.3.9 修改是整个脚本切换系统的重要改版。

此前中切时：

```text
特判切
↓
找不到
↓
全局切换
```

新版本加入：

> 中切独立特判切。

也就是说，中切可以有独立于普通全局切换的规则。

---

# 十三、中切独立特判切

示例形式：

```ini
精灵.ini

[循环]
A=特判切走
```

对应 `切换.ini`：

```ini
[T5000]
A=b
```

其含义是：

> 当前处于中切状态时，优先寻找 T 类独立特判。

如果找不到独立方案：

> 中切属于弱切，找不到就不切。

这一点和普通全局切换的行为有明显区别。

---

# 十四、中切以前的序号默认规则

截图特别指出：

> 以前 `[序号] 默认=` 在中切中是不生效的。

2.3.9 修改后：

> 现在会生效。

如果找不到：

```text
中切独立特判
```

则继续寻找：

```text
[序号] 默认=
```

再找不到才进入：

```text
全局切换
```

因此中切现在的层级更加丰富。

---

# 十五、特判切换的类型

截图中的切换系统可以归纳成：

```text
死亡切换类
├─ [S序号] 死切特判切
├─ [序号] 精灵特判切
├─ [死亡切换] 死切全局切
└─ 兼容老脚本

活切切换类
├─ [击杀] 击杀切
├─ [T序号] 独立特判切
├─ [序号] 精灵特判切
└─ [切走] 全局切
```

其中：

```text
S
```

主要与死切特判有关。

```text
T
```

主要与独立特判切有关。

---

# 十六、死切系统：2.3.9 的核心变化

2.3.9 以后：

> 死切和中切分开。

并且加入：

- 死切特判切；
- 中切独立特判切；
- 死切登场；
- `[S序号]`；
- `[T序号]`。

这是整个脚本体系最重要的版本变化之一。

---

# 十七、死切的实际判断顺序

新版死切逻辑：

```text
我方死亡
   ↓
是否存在死切特判？
   ├─ 有 → [S序号] 死切特判切
   │
   └─ 无
       ↓
   [死亡切换]
       ↓
   有 → 切换
   无 → 强制按照顺序切
```

这里的“死切特判”使用：

```ini
[S序号]
```

---

# 十八、[S序号] 存在时会发生什么

这是新版最重要的覆盖规则：

> 只要整个 `切换.ini` 中存在一个 `[S序号]`，死切时就不再走普通 `[序号]` 的精灵特判切。

也就是说：

```text
存在任何一个[S序号]
        ↓
死切进入 S 体系
        ↓
找不到匹配 S
        ↓
进入[死亡切换]
```

而不是：

```text
S 找不到
 ↓
普通[序号]
```

这正是很多旧脚本迁移到新版后行为发生变化的根源。

---

# 十九、为什么旧脚本仍然兼容

如果整个脚本：

> 一个 `[S序号]` 都没有。

则旧脚本继续使用以前的：

```text
[序号]
↓
精灵特判切
```

也就是：

```text
没有任何 S
↓
保留老的精灵特判机制
```

因此新版加入 `[S序号]` 并没有破坏旧脚本。

---

# 二十、死切特判的实例

例如：

```ini
[死亡切换]
默认=10

[S10]
默认=3550

[10]
默认=5000
```

那么：

- 精灵死亡后；
- 如果存在 `[S10]`；
- 就优先使用 `[S10]`；
- 不再用 `[10]`。

---

# 二十一、死亡切换

如果：

```text
[S序号]
```

没有找到对应方案，则进入：

```ini
[死亡切换]
```

例如：

```ini
[死亡切换]
默认=3512 4500 3577 4510
```

这表示死切无法找到特判目标时，按照配置中的候选精灵继续处理。

---

# 二十二、死切失败后的强制行为

如果：

```text
死切特判
```

和：

```text
死亡切换
```

都没有找到有效方案：

> 会进入强制按照顺序切换的逻辑。

因此死亡状态最终不会无限停留在当前精灵。

---

# 二十三、[S序号] 实例

截图中出现了类似：

```ini
[S10]
默认=3550
```

其含义就是：

> 发生死切，并且被击杀的精灵是 10 时，死切特判选择 3550。

---

# 二十四、[T序号] 实例

截图中：

```ini
[T10]
默认=3550
```

这是与中切独立特判切对应的形式。

即：

> 当前使用独立特判切时，根据对方或对应精灵序号进入 T 方案。

---

# 二十五、普通精灵特判与独立特判的区别

必须区分：

```text
[序号]
```

和：

```text
[T序号]
```

前者：

> 普通精灵特判。

后者：

> 独立特判切，主要用于新版中切逻辑。

因此同一个敌方精灵可以有：

```ini
[10]
默认=5000

[T10]
默认=3550
```

这并不冲突。

它们属于不同战斗状态下的两条路径。

---

# 二十六、切换系统总图

可以用下面的概念图理解：

```text
                     我方需要换精灵
                            │
             ┌──────────────┴──────────────┐
             │                             │
            死亡                           活切
             │                             │
       死切特判 / S                     普通切换
             │                             │
      [S序号]是否存在？               特判切 / 全局切
       │            │
      有            无
       │            │
      S体系        老脚本[序号]
       │
       └────找不到────→ [死亡切换]
```

活切继续区分：

```text
              活切
               │
       ┌───────┴────────┐
       │                │
      中切             其他
       │
       ├─ T独立特判切
       │
       ├─ [序号]默认
       │
       └─ 全局切换
```

---

# 二十七、活切的击杀切换

1.8.6 开始支持击杀切换。

基本语法思路：

```ini
[击杀切走]
……
```

或：

```ini
[击杀]
默认=切走
```

---

# 二十八、击杀切换不等于强制切换

非常重要：

> “我方击杀对方”本身不会强制让我方换精灵。

只有：

> 在击杀逻辑中写了 `切走`

才会触发击杀切走。

因此：

```text
击杀成功
≠
自动换精灵
```

必须：

```text
击杀成功
+
击杀技包含“切走”
=
触发击杀切走
```

---

# 二十九、击杀切换界面

新版编辑器可以直接看到：

- 击杀切换；
- 中切换；
- 针对死切换；
- 死亡切换。

编辑器中的字段明确标注：

```text
中途切换（中切，占回合，对方精灵=更换精灵）
针对死切（不占回合，对方精灵=更换精灵）
死亡切换（不占出招回合，对方精灵=更换精灵）
```

同时：

```text
击杀切换（暂不生效）
```

也存在于编辑器界面中。

原文特别强调：

> 内置编辑器目前只能查看击杀切内容，不能直接修改，需要打开文本文件手动修改。

---

# 三十、击杀切换优先级

击杀切换的优先级是：

```text
双方特判
↓
我方指定精灵击杀对方任意精灵
↓
我方任意精灵击杀对方指定精灵
↓
默认>默认
```

即：

```text
我方 > 对方
```

---

# 三十一、击杀切换实例

例如：

```ini
[击杀切走]
默认>默认=5000
默认>10=3550
3577>默认=4500
```

含义：

```text
默认击杀默认 → 5000
默认击杀10   → 3550
3577击杀默认  → 4500
```

实际优先级：

```text
双方指定
  >
我方指定
  >
对方指定
  >
默认
```

---

# 三十二、击杀切换的默认保底

如果脚本写：

```text
击杀切走
```

则：

```text
默认>默认=
```

必须存在。

否则：

> 可能卡出招。

但：

```text
默认>a=
```

或者：

```text
a>默认=
```

可以没有。

---

# 三十三、击杀切走不再强制换人

2.2.9 修改后：

> 击杀切走找不到要切的精灵时，不再强制切。

因此：

```text
找得到目标
→ 切

找不到目标
→ 不切
```

可以在：

```text
默认>默认=
```

中提供兜底。

---

# 三十四、击杀切走与普通切走的关系

如果在击杀配置中：

```ini
默认=切走
```

则：

> 触发击杀切走。

并且：

> 击杀切走中写“特判切走”和“切走”的效果等效。

---

# 三十五、击杀技只能写一招

击杀技是特殊动作。

例如：

```ini
[击杀]
默认=31581
```

只能使用一招。

不能写：

```ini
[击杀]
默认=技能1 技能2 技能3
```

把它当普通循环使用。

原规则明确：

> 击杀技只会出一招，第二个写了也不生效。

---

# 三十六、击杀技为什么只能有一招

因为击杀技对应的是：

> “上一回合已经发生击杀”这一特殊状态。

击杀后的下一回合：

- 系统知道对方死了；
- 但一开始还不知道对方换成谁。

所以此时只能执行一次特殊动作。

之后才回到正常的目标判断。

---

# 三十七、击杀后的时间轴

这是理解脚本系统非常关键的一张逻辑图。

假设：

```text
第 n 回合
我方击杀对方精灵 A
```

则：

### 第 n+1 回合开始

系统知道：

```text
A 被击杀
```

但不知道：

```text
对方换成谁
```

因此：

```text
优先击杀特判(A)
        ↓
没有
        ↓
击杀默认
        ↓
没有
        ↓
循环默认1
```

---

# 三十八、第 n+1 回合结束

此时系统已经知道：

```text
对方换上精灵 B
```

所以：

> 下一次判断时已经能够根据 B 的具体情况进入循环特判。

---

# 三十九、第 n+2 回合

优先判断：

```text
对方 B 是否有循环特判？
```

有：

```text
循环特判1
```

没有：

```text
循环默认2
```

这里的“默认2”非常重要。

因为：

> 前一个回合已经执行过击杀技或者循环默认1，对应的效果已经产生。

---

# 四十、击杀后的出招优先级

综合流程图，可以总结：

```text
对方切
   >
击杀
   >
登场
   >
循环
```

也就是说，在存在多个可能状态时，优先级并不是简单的“当前脚本第几个技能”。

而是：

> 对方状态变化 > 击杀事件 > 登场事件 > 普通循环。

---

# 四十一、循环系统

循环是最基础的常规出招逻辑。

例如：

```ini
[循环]
技能=36655 36657 36656
[击杀]
12=切走
```

可以通过精灵自身的循环和针对敌方精灵的特判进行组合。

---

# 四十二、循环特判

例如：

```ini
[循环]
技能=灵绳
玲冷吟唤=蓝之初醒
```

其核心就是：

> 遇到特定敌方精灵时，不再走默认循环，而进入对应特判方案。

---

# 四十三、登场技不会自动进入循环

比如：

```ini
[登场]
默认=5
```

即使这次登场结束后没有死亡、切换等事件：

> 也不会把“5”无限重复。

登场技是一次性的。

完成后：

```text
进入循环
```

---

# 四十四、普通登场的实际优先级

可以理解成：

```text
同起登场
   ↓
对面是否切精灵？
   ├─ 是 → 循环
   │
   └─ 否
       ↓
   有没有登场技？
       ├─ 没有 → 循环
       │
       └─ 有
          ↓
        登场技
```

---

# 四十五、中切登场的实际优先级

中切：

```text
中切登场
   ↓
对面是否切精灵？
   ├─ 是 → 循环
   │
   └─ 否
       ↓
   我方是否切精灵/被驱逐？
       ↓
   是否存在中切登场技？
       ├─ 没有 → 循环
       └─ 有 → 中切登场技
```

---

# 四十六、死切登场

2.3.9 增加：

```ini
[死切登场]
```

行为：

```text
有[死切登场]
    ↓
死切时使用[死切登场]

没有[死切登场]
    ↓
死切时仍使用[登场]
```

这就是新旧脚本兼容机制。

---

# 四十七、死切登场和普通登场同时存在

例如：

```ini
[登场]
默认=5

[死切登场]
默认=hp pp
```

那么：

```text
同起 → 5

死亡换人 → hp pp
```

不会互相覆盖。

---

# 四十八、特判切走

普通精灵脚本中可以直接写：

```ini
[循环]
默认=特判切走
```

或：

```ini
[登场]
默认=特判切走
```

但特判切走仍需要到：

```text
切换.ini
```

中寻找真正的目标精灵。

---

# 四十九、切走失败时的默认行为

例如：

```ini
[循环]
启灵元神=切走
```

当：

```text
启灵元神
```

无法切换时：

> 不会因为“写了切走”就一直卡住。

而是继续执行后面的默认逻辑。

如果只有一个切走：

```ini
启灵元神=切走
```

切换失败后：

> 会执行默认技1。

下一回合仍然会再次检查该切换条件。

---

# 五十、如何实现“切失败 → 技能1 → 再切 → 技能2”

写：

```ini
启灵元神=切走 默认1 切走 默认2
```

这样才能表达：

```text
尝试切
 ↓
失败 → 默认1
 ↓
再次尝试切
 ↓
再次失败 → 默认2
```

而不是只写一个：

```ini
启灵元神=切走
```

后期待系统自动进入默认2。

---

# 五十一、两个切走不能相邻

这是最容易导致“卡出招”的语法错误之一。

以下都是错误：

```text
a 切走 切走 b
```

```text
切走 a 切走
```

原因：

> 两个切走相邻。

而且：

> 首尾也算相邻。

---

# 五十二、允许的切走结构

允许：

```text
切走
```

某些位置可以单独出现。

也允许：

```text
切走 技能 切走 技能
```

以及：

```text
技能 切走
```

关键原则：

> 不能让两个切走成为相邻节点。

---

# 五十三、循环中的单独切走

特别注意：

> 循环里面单独写一个“切走”可能造成空过。

因此：

```ini
[循环]
默认=切走
```

不是推荐的写法。

但：

```ini
[登场]
默认=切走
```

可以成立。

---

# 五十四、切换系统中的“活切”与“死切”

可以总结成：

```text
活切
├─ 对方触发的普通切
├─ 特判切
├─ T 独立特判切
├─ 击杀切
└─ 中切

死切
├─ S 死切特判
├─ 死亡切换
└─ 死切登场
```

两者不要混写。

---

# 五十五、`[S序号]` 与 `[T序号]`

开发者可以把它们简单记成：

```text
[S]
= 死切专用特判体系

[T]
= 独立特判切体系
```

它们不是普通 `[序号]` 的别名。

---

# 五十六、精灵名称模糊匹配

2.3.9 后：

`BP.ini` / `banpick.ini`

条件中的精灵可以直接写名称。

例如：

```ini
[圣灵谱尼/天启帝君/武心婵]
```

不再强制要求：

```ini
[5000/3550/4500]
```

首发和出战也可以进行名称模糊匹配。

# 五十七、选择性 BP

适用场景：

> 主力阵容中的某个关键组件被 Ban 后，需要自动采用另一套阵容。

基础：

```ini
[BP]

禁用=5000 3577 3788
首发=4500
出战=4500 2667
```

条件：

```ini
[5000/3550/4550]

首发=3512 4515 3809
出战=3506 4554 2667 3237 4515 3550 5000

[5000/3550/3512]

首发=4554
出战=3506 4554 2667 3237 4515 3550 5000
```

---

# 五十八、选择性 BP 的判断顺序

除默认 `[BP]` 外：

> 所有条件从上到下判断。

所以：

```text
更具体的条件
```

应写在：

```text
更宽泛的条件
```

前面。

例如：

```ini
[5000/3550/3577]
……

[5000/3577]
……

[5000]
……
```

这样才能优先匹配三条件。

---

# 五十九、条件数量

支持：

```text
1 个
2 个
3 个
```

条件。

推荐：

```text
3条件
↓
2条件
↓
1条件
```

# 六十、3V3 模式的限制

3V3 模式：

> 使用 1 个或 2 个条件。

因为：

> 如果写 3 个条件，会走默认。

# 七十六、死切体系的最终优先级

新版可以简化为：

```text
我方死亡
   ↓
是否存在任何[S序号]？
   │
   ├─ 否
   │    ↓
   │  老的[序号]精灵特判
   │
   └─ 是
        ↓
      [S序号]死切特判
        ↓
      找不到
        ↓
      [死亡切换]
        ↓
      找不到
        ↓
      强制按顺序切
```

# 七十七、活切体系最终优先级

普通活切可以理解成：

```text
触发切换
 ↓
对应独立特判？
 ↓
对应精灵特判？
 ↓
全局切换？
 ↓
找不到就不切 / 执行后续技能
```

而中切则是独立的一套逻辑。

# 七十八、中切体系最终优先级

```text
中切
 ↓
T独立特判切
 ↓
找不到
 ↓
[精灵]默认
 ↓
找不到
 ↓
全局切换
 ↓
找不到
 ↓
中切为弱切，不切
```

这就是截图中“中切为弱切，找不到就不切”的核心含义。

# 七十九、特判切与普通切换的本质区别

可以简单记：

```text

切走
=
可能进入全局切换
```

特别是新版：

```text

```

具有更加独立的路径。

# 八十一、调试方法

遇到“脚本不按预期走”时，不要先怀疑技能顺序。

应该按下面顺序排查：

```text
当前到底是什么状态？
↓
同起 / 中切 / 死切 / 击杀？
↓
是否存在对应特判？
↓
是不是 S/T 体系覆盖了旧体系？
↓
有没有找到默认保底？
↓
是不是切走失败？
↓
是否因为锁切？
↓
是否因为两个切走相邻？
↓
是否因为击杀后信息尚未更新？
```

# 八十二、常见“卡出招”原因

## 1. 两个切走相邻

错误：

```text
切走 切走
```

---

## 2. 循环中只写切走

可能产生：

> 空过。

---

## 3. 击杀切走没有 `默认>默认`

可能：

> 卡出招。

---

## 4. 死切存在 S，但作者还按旧 `[序号]` 设计

结果：

> `[序号]` 在死切时不再生效。

---

## 5. 中切设计只写了普通 `[精灵]`

新版中切：

> 可能需要 `[T精灵]` 或中切独立特判体系。

---

## 6. 中切特判方案只有部分目标

可能导致：

> 当前目标没有中切特判方案，但又不回退到普通中切登场。

---

## 7. 被控吃药不占出招回合

可能：

> 无限吃药。

# 八十三、击杀逻辑的开发模板

可以把一个常规击杀场景抽象成：

```ini
[击杀]
目标A=技能1
默认=技能2
```

再：

```text
是否切走？
```

如果要击杀后换人：

```ini
[击杀]
默认=切走
```

然后确保：

```ini
[击杀切走]
默认>默认=……
```

存在。

---

# 八十四、击杀后的“重置出招”

截图特别说明：

> 对方切精灵后，当前循环出招方案会重新判定。

即：

```text
循环技
↓
对方切人
↓
重新判断对方精灵
↓
重新决定循环特判
```

因此敌方换人相当于：

> 打断旧的循环对象判断。

---

# 八十五、击杀后的“重置”不是立即完全重置

击杀后存在两个阶段：

```text
n+1
```

时：

> 知道对方死了，不知道新精灵是谁。

所以执行：

```text
击杀特判
/
击杀默认
/
循环默认1
```

到了：

```text
n+2
```

时：

> 已经知道新精灵 B。

因此进入：

```text
循环特判1
/
循环默认2
```

---

# 八十六、击杀流程的完整图解

```text
第n回合
我方击杀精灵A
       ↓
第n+1回合
       ↓
是否有击杀特判A？
   │
   ├─ 有 → 击杀特判1
   │
   └─ 无
        ↓
是否有击杀默认？
   │
   ├─ 有 → 击杀默认
   │
   └─ 无 → 循环默认1
       ↓
本回合结束
       ↓
知道对方换成B
       ↓
第n+2回合
       ↓
B是否有循环特判？
   │
   ├─ 有 → 循环特判1
   └─ 无 → 循环默认2
```

# 八十九、开发者的核心认知

整套脚本系统最重要的原则不是：

> “技能一打完技能二”。

而是：

> “当前发生了什么事件，系统现在知道什么信息，因此应该进入哪一个状态树”。

尤其是击杀和切换存在信息延迟：

```text
击杀当回合
```

知道的是：

```text
对方死了
```

却不一定知道：

```text
对方换谁
```

所以击杀后的第一回合与第二回合不能写成完全一样的循环。

同理：

```text
中切
```

与：

```text
同起
```

回合状态不同，所以登场技必须分离。

而：

```text
死切
```

又与：

```text
中切
```

完全不同，所以 2.3.9 才将两者彻底拆开。

# 九十、最终开发规范

制作新版脚本时，建议遵循以下规则：

**规则 1：**

永远先区分：

```text
同起
中切
死切
击杀
```

**规则 2：**

使用新版 S/T 系统时，要确认是否会覆盖旧 `[序号]` 逻辑。

**规则 3：**

所有击杀切走都必须提供：

```text
默认>默认
```

**规则 4：**

切走不要相邻。

**规则 5：**

循环中不要单独写一个 `切走`。

**规则 6：**

击杀技只能写一招。

**规则 7：**

中切特判要检查是否存在“部分覆盖”问题。

**规则 8：**

需要独立死亡登场时写：

```text
[死切登场]
```

否则系统会兼容旧脚本使用：

```text
[登场]
```

**规则 9：**

高级药逻辑使用小写：

```text
hp
pp
```

**规则 10：**

被控吃药一般推荐开启：

```text
占用出招回合
```

# 九十二、最终结论

“重聚巅峰”脚本并不是简单的技能序列文件，而是一套以**战斗状态、信息获取时机、精灵切换原因和优先级**为核心的规则系统。

其中最关键的结构可以压缩为：

```text
BP
↓
首发/出战
↓
当前状态
↓
切换原因
↓
特判优先级
↓
对应登场
↓
击杀/切换事件
↓
重新判定循环
```

2.3.9 是切换系统的重要分水岭，因为它把：

```text
死切
中切
活切
```

之间的关系进一步拆开，并加入：

```text
[S序号]
[T序号]
[死切登场]
中切独立特判切
```

2.4.2 又继续加入：

```text
中切特判登场
```

因此如果开发的是新版脚本，不能再完全按照早期“普通特判切 + 普通登场”的思路制作。

真正稳定的脚本必须建立：

```text
事件
→ 状态
→ 特判
→ 默认
→ 保底
```

这五层关系。

一句话概括：

> **先判断发生了什么，再判断当前处于同起、中切、死切还是击杀状态；然后按照对应状态的特判优先级选择方案，找不到时进入正确的默认和保底逻辑，最后才回到普通循环。**

这就是整套“重聚巅峰”脚本系统最核心的开发思想。
